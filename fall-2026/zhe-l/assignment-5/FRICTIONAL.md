- **What I understand now / still do not understand:** Through this assignment I started to understand how the parts of shader code work together, rather than just changing numbers in an example.

  I now know that UV is the 2D coordinate used to read a texture, not the model's position in the scene. `texture(rust_albedo, UV)` reads the texture at a given position; the `.rgb` after it takes the three colour components, and `.r` takes only the red channel. A colour texture reads back colours, while the values read from a height texture can be used to decide where rust shows. Both are texture reads, but what the data is used for can be completely different.

  I also understand what a uniform is: a parameter declared outside the functions and passed in by the material Inspector or by game code. For example, `wear_amount` controls how much rust shows, `texture_scale` controls how large the texture repeat is, and `pad_light_data` controls the screen brightness. The default in the declaration gives the initial setting, and the material or code can override it. By contrast, `height`, `width` and `w` in `fragment()` are local variables used while computing the current fragment, and `const` holds values in the code that never need to change.

  I used to think of `vertex()` as "the function that computes UVs"; now I know it is the function that processes vertices, and my crate shader just happens to use it to compute UVs. In `crate_wear.gdshader` I first read `NORMAL` to tell which way the surface faces, then take two components of `VERTEX` as the coordinates, and finally multiply by `texture_scale`. I do not change `VERTEX`, so the model's shape does not change; assigning to `VERTEX` would move vertices. The UV made here is interpolated and passed on to `fragment()`.

  `fragment()` computes the material properties from the current fragment's data. My crate shader first reads the rust colour and the height, then uses `smoothstep()` to get the transition value, uses `1.0 - ...` so that low places get more wear, and finally uses `mix()` to mix the colour and roughness of paint and rust. I can now follow the data flow between these lines: the height decides `w`, and `w` decides `ALBEDO` and `ROUGHNESS`; the lines do not each produce an effect on their own.

  I also understand that hints are not just notes after the code. `hint_range` mainly controls how the Inspector takes input, while `source_color` affects the colour-space conversion, and the filter and repeat settings affect texture sampling. So the same grey image read through two different samplers can show different brightness. `ALBEDO` is the material's base colour and is not necessarily the RGB in a screenshot; even with `unshaded`, the colour conversion before display has to be considered.

  Finally, the tablet brightness experiment taught me that the Inspector's range and the value the code actually uses must be understood separately. Although `pad_light_data` is marked with the range 0–1, code can still pass in 2.0. `mix()` does not limit it to 1 but keeps computing, and the screen ends up pure white. If I really need to limit a value, I should use `clamp()` explicitly in the code and not rely only on `hint_range`.

  What I still do not understand (the three points I chose for the film's verdict): only captures, never a headless run, show that the GPU really decodes sRGB; why the correct normal map scores 0.2 rather than 0 in the curl check, which TEST-REPORT puts down to 8-bit quantisation; and what `hint_roughness_normal` does to roughness on import.
