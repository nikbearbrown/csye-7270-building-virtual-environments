# Capture plan: Local, World and Screen Space

**What this is.** Every Godot render, editor frame and screenshot the build session must record for this film, with the exact shader file, the scene script, the motion over time, the length, the renderer, what is on screen at the 50 % and 85 % marks and the result already verified. Nothing for the film is recorded yet except the editor frames (section Editor frames, recorded by script on 2026-10-13); the numbers come from planning runs in `evidence/planning-checks/`.
**Why.** Films show only what was really done and recorded. This is the list of things to really do, written so a medium-effort session can do them without further judgment. Most captures need a camera, a moving sprite or a second node, which the Shader Lab cannot do, so each one has a scene script that was run end to end and probed (`capture_scenes.gd`, `verify12.gd`).
**Found.** 12 Godot renders (all custom scenes, all Forward+), 1 editor capture (E1, two whole frames, DONE by script on 2026-10-13; the optional E2 is also recorded), 1 docs screenshot (D2) and 1 terminal log (B14). All 17 shaders compile in the Lab and give the same probes on Forward+ and on Compatibility; every scene script was run and its 50 % and 85 % frames looked at (`png/capture-scenes/`, contact sheet included). Two routes are used (the series rule of 2026-10-13, below): eleven captures go through the 4K SubViewport route because their shaders work in world or local numbers; **C10, the four tiles, is captured at 1920 by 1080 at scale 1** because three of its shaders read window pixels (`FRAGCOORD`, `SCREEN_PIXEL_SIZE`, `VERTEX` in `fragment()`). Measured both ways (`verify13.gd`), the four tiles paint the same gradient on either route, so nothing about the picture depends on the choice; the rule is followed anyway.

## Conventions for every capture

- **Scene scripts.** Each capture is one object from `evidence/planning-checks/capture_scenes.gd` (`CaptureScenes.make("C01")`), wrapped one per file in `evidence/planning-checks/capture-scenes/capture-c01.gd` and so on, for the harness's `--scene PATH.gd` option. Contract: `build(parent, audio_length)` creates the nodes under a node already in the tree (the logical canvas, or the SubViewport of the scene's route); `at(t)` puts every node in its state at clip time `t` seconds and is a pure function of `t` (no tweens, no timers), so the harness calls `at(frame / 30.0)` before each frame and every frame is reproducible; past `audio_length` the last state holds; `route()` returns the logical canvas and the render size (default 1280 by 720 rendered at 3840 by 2160; C10 returns 1920 by 1080 for both, see "Canvas and route" below). Copy `capture_scenes.gd`, `scenes_lib.gd`, `sky_lib.gd` and the wrappers into the harness project's root (they load each other as `res://…`); the shaders are read from this film's `lab-shaders/` (absolute path in `scenes_lib.gd`, override with the environment variable `LOCAL_WORLD_SHADERS`). Motion windows are fractions of the beat's measured audio, so pass the measured length to `build`; the table also gives seconds at the estimate.
- **Canvas and route (read this before recording).** 30 fps, offline at a fixed tick rate (so nothing here says anything about real-time frame rate). The series rule (`GLOSSARY.md` "Series conventions", `COMPONENT-SPECS.md` "Capture harness"): shaders that read window pixels (`FRAGCOORD`, `LIGHT_POSITION`, `LIGHT_VERTEX`, `SCREEN_PIXEL_SIZE`) are captured at the size they are shown, 1920 by 1080 at scale 1, because the 3x SubViewport route changes their numbers (here, measured in `verify8.gd` R1: a sprite at (600,400) seen by a camera at (890,460) still reads local (-64,-64) and world (536,336), but the screen built-ins read 3x, 858 and 708 for the corner pixel that is (286,236) logically, and `SCREEN_PIXEL_SIZE` reads 1/3840). Every scene script says which route it needs in `route()` (`capture_scenes.gd`): the harness builds a SubViewport of `route().render` and, when `render` differs from `canvas`, sets `size_2d_override = canvas` with stretch on.
  - **The 4K route (11 captures: C01 to C09, C11a, C11b):** a 1280 by 720 logical canvas rendered at 3840 by 2160 (`size = 3840x2160`, `size_2d_override = 1280x720`, stretch on). Their shaders read local numbers (`VERTEX` in `vertex()`), world numbers (`MODEL_MATRIX`), texture or UV numbers, or `SCREEN_UV` (a fraction of the viewport), none of which depends on the render size. C11a and C11b use `SCREEN_UV.x * 20.0`, a fraction.
  - **1920 by 1080 at scale 1 (1 capture: C10):** a SubViewport of 1920 by 1080 with no override, the scene laid out on a 1920 by 1080 canvas (four tiles of 960 by 540). Shaders 10, 12 and 13 of this scene read window pixels and multiply them by `SCREEN_PIXEL_SIZE`. In this window `FRAGCOORD.x` reads 838 at pixel 838 and `SCREEN_PIXEL_SIZE.x` reads 1/1920 (`verify13.gd` B2).
  - **Same picture either way, for the record:** `verify13.gd` A runs the four tiles through the 3x route (worst difference from the exact gradient 0 of 255 over 144 pixels) and B at 1920 by 1080 (also 0): the shaders multiply a pixel count by the pixel size, so both scale by 3 and the fraction is unchanged. C10 uses the 1920 by 1080 route because the rule says to, not because the picture differs.
  - **Nothing on screen in this film is a screen pixel number read from a capture.** The screen numbers shown (286, 236 and 186, 236 in B07; 286.5, 236.5 in B30; 1279.5, 719.5 in B31; 128 and 256 in B34) were measured in a 1280 by 720 window by the planning scripts and are typed as readouts, labels or captions; B07's `videoLabel` and B31's caption say "1280 by 720 window", and B33's label says "1920 by 1080 window".
- **Renderer.** Forward+ on Apple M4 Pro, Godot 4.7.2; say it in every `videoLabel`. The 17 shaders were also run on Compatibility (`lab-results-gl_compatibility.jsonl`: identical probes) and the position checks too (`run-7-*.log`).
- **Stage.** Clear color `#D9D5CA` (the Lab's), teal `#5FA391` sprite, cream `#FAF9F5` eyes. No Godot `Label` nodes anywhere: every word on a capture is a ShaderLab readout (crisp at 4K).
- **Assets (all procedural, no external art).** `sky`: `sky_lib.make_sky(1536)` (seed 7): tileable, one tile = 512 world pixels (texture 1536 px so it is 1:1 at 4K), indigo with cream stars and one ringed planet per tile at tile position (340,240): planets on the stage at x = 340 and 852, y = 240. `blob`: `scenes_lib.blob_texture(256, true)`, the Lab's test sprite with a 1.5 px soft edge (the blob is 154 px across, centered in its 256 px art). `checker`: `scenes_lib.checker_texture(256)`. Regenerate the sky PNG with `godot --headless --path <scratch project> --script res://make_sky.gd -- <out dir>`; frames of it are in `evidence/planning-checks/png/scene-sky-512.png`.
- **Camera.** `Camera2D`, position smoothing off (the default), anchor mode default; the scene scripts set the exact positions below.
- **Backdrop.** "Faint backdrop" = a `ColorRect` sized to the stage (or larger), material `02-sky-world.gdshader` with the same `sky` texture, `modulate.a` as stated. It makes the same lookup as a world-locked sprite, so it lines up by construction.
- **Record length.** 1 to 2 s longer than the estimated audio; the last frame holds; the build trims to the audio.
- **Output.** `TK/runtime/remotion/public/local-world-and-screen-space/<name>`; names as the lanes use them. The ShaderLab cues and readouts already avoid 45 to 55 % of the beat.

The output has the engine banner, **one line the script itself prints** ("fragment() runs once for each pixel the shape covers; sets its color": the definition, on screen where the voice first says "fragment", in the same full ink as every other line), then the engine's own five marked source lines and the `SHADER ERROR` line. ## Not captured on purpose

No GPU timing. No real-time frame-rate claim. No screen pixel number read from a capture (the screen numbers shown are typed readouts measured in a 1280 by 720 window; the 4K route would triple them). No `TIME`-driven shader (none is used in this film). No Godot text rendering.
