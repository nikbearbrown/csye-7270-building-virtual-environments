Most people meet a shader as a strange file of math. One idea makes it readable. A shader does not paint the whole screen. It decides the color of one pixel, and the graphics card asks it about every pixel at once. Five terms, the GPU is the graphics chip, many small workers running at once. A pixel is one dot of the picture. A vertex is a corner point of a shape. A texture is an image, a shader can read, and a material tells Go Do how to draw a surface. A game can work and still look flat. Same sprite, same background, nothing broken. A shader is the part that decides how it looks, the wobble, the glow, the water, the outline. A shader is a small program that runs on the graphics card, the GPU. It decides how something is drawn. Your game code decides what exists and where. The shader decides what each part looks like. Why a second chip, the CPU is a few fast workers doing one job after another. The GPU is a crowd of small workers, all doing the same job at once. A picture is millions of identical little jobs. Here is the slow way, a GD script loop colors every pixel of a full HD picture, one at a time, that is over 2 million calls for one picture, watch what it costs. On this Mac, that loop took about 55 milliseconds. A game running at 60 frames per second has 16 and a half milliseconds for everything. This is one gradient, and it is more than three times the whole budget. The shader way describes one pixel. This line says, the red amount is how far across the shape this pixel sits, nothing loops. The graphics card runs the line for every pixel and the gradient appears. Drawing that same gradient this way costs the processor about 400s of a millisecond, only to hand over the job. The graphics card did the pixels. Its own time could not be read on this setup, so there is no number for it. So a shader flips the question, not for each pixel do this. Instead, write down what one pixel should do and let the card do it everywhere. A shader decides the color of one pixel. Where does a shader live in a file? You attach it to a node through a material. The node holds a shader material and the shader material holds your shader. In the editor, that is a few clicks. In the node's material slot, choose shader material under new, click it and in its shader slot, choose new shader. Set the mode to canvas item since it starts on spatial and create it. Go Do opens the shader editor. What you type there is Go Do's own shader language. It is similar to a standard one called GLSL, but simpler. If you can read a few lines of GD script, you can read it. It is strict about types and statements end in semicolons. The first line of every shader says what it is for. Canvas item is for 2D drawing an interface. Spatial is for 3D. Particles, Sky and Fog are for those. This film uses Canvas item. The ideas carry over to 3D with a few different names. The smallest working shader has one function in one line. In the function called fragment set color to four numbers. Red, green, blue and how visible it is. 1-0-0-1 pure red fully visible. A shader can have up to three special functions and the engine calls them for you. Vertex, fragment and light. You write what each one does. Go Do decides when it runs and how many times. Vertex runs once for each vertex, each corner point of the shape. A plain rectangle has four corners, so vertex runs four times. Its job is to place the corners. A real run, this vertex pushes the bottom two corners 50 pixels to the right and leaves the top two alone. The whole picture lines because the card fills in everything between the corners. Between the corners you calculate nothing. The left edge slides evenly from top to bottom. 50 pixels over 128 rows. That is why vertex alone cannot ripple a plain rectangle. Four corners can only make straight edges. Fragment runs after the corners are placed. It runs once for each pixel the shape covers and its job is to set that pixels color. The shape is already decided. Now the card asks about every pixel inside it. You will hear this called a pixel shader or a fragment shader. Same job to names. Microsoft's direct 3D says pixel. Open GL, Vulcan and Go Do say fragment. The careful word is fragment because a fragment is a pixel to be. It is only a pixel to be because it can still be thrown away or blended with others. This shader says discard for the right half. Fragment ran there. No pixel came out and the background shows through. The third function light runs once for each light that touches a pixel. Two lights, two runs and the results add. If you write light it replaces Go Do's default lighting even when it is empty. Here we only name it. So the order of work is fixed. First vertex places the corners. Then the card fills in the shape. Then fragment colors each pixel. Information flows one way forward. Inside these functions the engine hands you values called built ins written in capital letters. Some come in like a pixels address in the time. One goes out the color you set, which ones exist depends on the function. So far vertex runs once per corner and places things. Fragment runs once per pixel and colors things. Light runs once per pixel for each light and lights things. A shader that always draws the same red is not much use. Your game needs to say more red now less red later. But the shader lives on the graphics card out of reach. How do you talk to it? With a uniform a uniform is a value you declare outside the functions and set from outside the shader. Here is one called red from zero to one. The shader reads it. The shader can never change it. In the editor that line becomes a slider. In the inspector under shader parameters there is a control labeled red, drag it and the picture changes while you watch. Three uniforms make a color mixer. Red, green, blue each its own slider. The shader puts the three numbers together into a color. The part after the colon is a hint it tells the editor how to show the uniform. A range adds a slider bar. Source color gives a color swatch that opens a picker. A hint shapes the editor, not the math. A hint does not clamp if your game code sets the value to seven. The shader receives seven. The slider only guards the editor. If a range matters, enforce it in your code as well. From the game you set a uniform with set shader parameter. Get the nodes material then pass the uniforms name and a value. The name is case sensitive and it must match the shader exactly. Get the name wrong and nothing happens. No error. The value is stored as an unused parameter. The real uniform keeps its default and the effect never appears. When a shader ignores your game check the spelling first. You can animate a uniform too. Set it starting value from code then tween it and the shader follows every frame. Skip the first step and the tween has nothing to start from. That is how a shader answers to gameplay. A uniform is one value the same for every pixel in the draw. Some inputs must differ because each pixel needs to know where it is. The engine hands those in and they are different for every pixel. Two kinds of input then a uniform is set by you a built in is set by the engine. Both are names the shader can read and some built in like the time are the same for every pixel too.
