# Capture plan: Reading the Screen

**What this is.** Every Godot render the build session must record for this film, with the scene script that makes it, the shader files, the values over time, the length, the renderer, what must be visible at the 50 % and 85 % marks and the result already verified. Nothing is recorded yet. Unlike the layout of the first film in the series, **every capture scene is already written and has run**: they are small GDScript files in `evidence/planning-checks/`, drawn by the same routes the captures use (see Routes below).
**Why.** Films show only what was really done and recorded. This is the list of things to really record, written so a medium-effort session can do it without further judgment: for each capture, one command.
**Found.** 23 captures (C01 to C23), serving 25 beats (C01 serves B01 and B28, C06 serves B16 and B17). All are scripted, offline renders on a fixed 30 fps tick; none needs the editor or a screen recording. All 15 shaders compile in the Lab (`lab-results.jsonl`), the 23 scenes were checked at 50 % and 85 % (`run-15`, `run-16`) and rendered at 10, 50 and 85 % as `frames/` (69 PNGs). Everything behaved the same in Forward+ and Compatibility except the strength of the blur (C13); captures are labelled Forward+. **Two routes** (see Routes): 22 captures go through a 3840 x 2160 SubViewport over a 1280 x 720 canvas, and C13 (the mip-level blur) is captured natively at 1920 x 1080 at scale 1, because a blur level counts texels and is less than half as strong on the 4K route (`verify10.gd`, `run-25`, `run-26`). One thing is not captured on purpose: GPU time.

## The scene contract (read this before recording)

- A capture scene is a GDScript file that extends `rts_scene.gd` (same folder). It is a **pure function of time**: the driver sets `duration` (the beat's measured audio, in seconds) and `canvas_size` (1280 x 720), then calls `set_time(t)` once per frame with `t = frame / 30`. Every keyframe is written as a fraction `u = t / duration`, so the same scene fits any beat length. **Record after the audio exists** and pass each beat's measured duration.
- `rts_lib.gd` builds the shared test world (the meadow: a 16 x 9 checker of two greens, a sand path, three trees, twelve flowers), the series' test sprite (the teal blob) and the health bar. The shaders are read from `res://lab-shaders/` (a copy of `../../lab-shaders/`; `run-checks.sh` makes the scratch project for you).
- **Driver:** `scene_capture.gd` renders one scene frame by frame through a 3840 x 2160 SubViewport over the 1280 x 720 canvas (or, with `--native`, through a SubViewport of the stated size at scale 1: C13 only), under `--fixed-fps 30` so `TIME` (ripples, the pool) repeats exactly. `capture_all.py` picks the route for each capture. Tested: 8 frames of C01 at 960 x 540 (`run-21-capture-driver-test-8-frames-960x540.log`; 7 of 8 frames differ from the previous one, as the water moves) and both routes end to end (`run-22`, `run-27`). One scene:
  `./csye-7270-building-virtual-environments/youtube/claude-liam-lecture-reading-the-screen/evidence/planning-checks/run-checks.sh capture scene_c01_pool <seconds> forward_plus --width 3840 --height 2160`
  writes `/private/tmp/claude-501/rts-checks/capture/scene_c01_pool/f00000.png ...`; then `ffmpeg -framerate 30 -i f%05d.png -c:v libx264 -pix_fmt yuv420p -crf 12 <name>.mp4` into `TK/runtime/remotion/public/reading-the-screen/` using the file name in the table. Check disk first: a 4K PNG sequence is large; render and encode one capture at a time and delete the frames.
- 22 pictures are 1280 x 720 logical, rendered at 3x; C13 is 1920 x 1080 logical at 1x. Do not upscale anything smaller; do not crop past the frame.
- **Offline fixed tick:** a capture says nothing about real-time frame rate. Nothing in the film claims one. Scripted motion (the walk, the slide, the pan, the dial) is labelled in each lane's `videoLabel`.
- The cream frames around windows are drawn on a high canvas layer so no screen reader ever copies them (a frame inside a copy would be flipped to near-black by an invert window).

Conventions for all captures: 30 fps; Forward+ (`--rendering-method forward_plus`); the route in the next section (3840 x 2160 through the SubViewport for every capture except C13, which is native 1920 x 1080); stage and world colours as in `rts_lib.gd`; output names exactly as in the table (the lanes use them).

## Routes (which size each capture is recorded at, and why)

The series asks for shaders that read physical pixels to be captured at the size they are shown, because the 3x SubViewport route changes anything counted in pixels or texels. This film's 15 shaders were checked one by one for that (`verify10.gd`, both renderers):

| Route | Captures | Why it is safe or needed |
|---|---|---|
| **A: 3840 x 2160 SubViewport over a 1280 x 720 canvas** (`size_2d_override`, crisp in the 4K master) | C01 to C12, C14 to C23 | Every shader here works in fractions: `SCREEN_UV`, sine of an address, `mix`, `dot`, `distance` on addresses. The one use of `SCREEN_PIXEL_SIZE` (07-spotlight) is the ratio of its y to its x, which is the same at any size with the same proportions. Measured: the spotlight scenes land within 1 canvas pixel of the 1280 x 720 result (C06 oval 639 x 357, C07 circle 357 x 357, C08 centroid on the player), in both renderers. |
| **B: native, a 1920 x 1080 SubViewport at scale 1, the scene built for a 1920 x 1080 canvas** (`scene_capture.gd --native --width 1920 --height 1080`) | **C13** | A mip level counts texels of the screen texture, and the screen texture has as many texels as the SubViewport has pixels. Inside the window, the level-4 picture differs from the sharp one (mean over the three channels, 0 to 1) by 0.037 in a plain 1280 x 720 window, **0.017 on route A** (less than half), and 0.028 on route B, in Forward+ (in Compatibility the same three are 0.021, 0.008 and 0.015). Looked at: on route A the checker pattern is still visible at level 4, so the film's "frosted glass" would not read; on route B it does. |

Rule for any capture added later: if its shader counts texels or pixels (`textureLod` on a mipmapped screen texture, `FRAGCOORD`, `SCREEN_PIXEL_SIZE` used as a size, `LIGHT_POSITION`, derivatives), use route B and say so here.

## Editor frames

None are needed. The Manim beats that show them (B11, B13, B33's chip) use those exact words. **Optional upgrade**, only if the build wants real editor frames instead of the drawings (nobody has to click or record by hand): the editor driver (`../_godot-shaders-series/editor-capture/README.md`, sections 5 and 7) records Godot's own editor by script, one PNG per named state, on a scratch project. For this film that means a scratch scene with a ColorRect under a CanvasLayer (Inspector > Layout > Anchors Preset open on "Full Rect"; Inspector > Mouse > Filter open on "Ignore") and a BackBufferCopy (Inspector > Copy Mode open on "Viewport"): write a state script by copying `../_godot-shaders-series/editor-capture/state-scripts/final/pilot-E2.json` and use the driver's steps `open_scene`, `select_node`, `unfold_group`, `press`, `open_option_button` and `click_control`, then `mark`. **Not yet tried:** these three states were not recorded on 2026-10-13, and the driver has not yet opened an Anchors Preset popup or a Mouse Filter dropdown (it has opened resource menus, a Create Shader mode list, the renderer menu and a color picker), so the first run of such a script is also its test; the shared Lab lock is held for the run (about 20 to 60 seconds).
