# Capture plan: Reflections

**What this is.** Every Godot render, editor frame and screenshot the build session must record for this film: the scene, the shader file, what moves when, the length, the renderer, what must be visible at the 50 % and 85 % marks, and the result already verified. Nothing for the film is recorded yet; the numbers come from planning runs in `evidence/planning-checks/`.
**Why.** Films show only what was really done and recorded. The scenes are custom (a pond, a hidden label map, three flat squares and a window), so this plan points at a tested scene library instead of describing node trees in words, and says exactly how to record each one.
**Found.** 19 Godot captures from ONE scene library (`evidence/planning-checks/capture_scenes.gd`, art from `pond_common.gd`, every shader a tested file in `lab-shaders/`), each run and probed on Forward+ on both capture routes (the experiments behind them were repeated in Compatibility). 2 editor frames (planning frames already recorded and looked at), 2 documentation screenshots. Nothing needs an interactive editor step: a scratch plugin selects the node. A capture tool (`capture_scene.sh`, driven by `capture_all.sh`) exists and was tested end to end (run-17): all 19 clips recorded at their beats' lengths, each 3840 x 2160, 30 fps and exactly length x 30 frames, looked at on a contact sheet (`evidence/planning-checks/png/contact-sheet-recorded-clips.png`); 13 minutes with the machine busy, so budget 10 to 15 minutes. One thing about the capture route changed the plan: a BackBufferCopy's Rect box counts render pixels, so C08 alone is recorded 1:1 (section "Which route each capture uses").

## Conventions for every capture

- 30 fps; 3840 x 2160 through the SubViewport native-size route over the 1280 x 720 logical canvas (`size_2d_override` with stretch; the art is built at 3x so edges stay sharp), except C08 (below); the Lab stage colour `#D9D5CA`; **Forward+** (the projects' default); offline fixed tick rate, so nothing here says anything about real-time frame rate; scripted movement and scripted tree changes are labelled "scripted" in `videoLabel`.
- **Every capture runs in a FRESH Godot process.** A rect-mode BackBufferCopy reads whatever earlier frames left in the back buffer (run-03 R4 shows stale pixels); C08 depends on it, and `capture_scene.sh` starts a new process per capture.
- Output: `./brutalist.art/runtime/remotion/public/reflections/<name>.mp4` (the name in the lane's `video`). **Audio first: every clip is recorded at the length of its beat.** The "planned length" in the table is only the scene's own default; `capture_all.sh` passes the beat's measured `actual_duration_s` (the layout's estimate before the voice exists) as `--length`, and the scene plays all its scripted events at the same fractions of the clip (run-15: the 50 % and 85 % probes do not move with the length; a 12 s clip of a 15 s scene gives exactly 360 frames). The lane's cue times are fractions of the beat, so they stay on the picture. If a beat is more than 1.4 times or less than 0.7 times the planned length the tool prints a `retime_warning`: look at the video.
- Tools: `evidence/planning-checks/capture_all.sh <out dir> [--only C07,C08] [--dry-run]` records them all (it reads the lanes and `beat_sheet.json`, runs `capture_scene.sh <ID> <out.mp4> [project dir] --length S` once per capture in its own Godot process; `--dry-run` prints the plan; the frames of each clip are kept in `${TMPDIR:-/private/tmp}/reflections-capture-frames/`, outside the Remotion public folder, until you delete them). If the shared harness `lab/capture.gd` has been built and can call a scene script every frame, it can replace the tool: the scene contract is at the top of `capture_scenes.gd` (`setup(id, shaders_dir, art_scale)`, `build(parent)`, `tick(t)`). `scene_runner.gd` is the checked stand-in; its `--times` option prints probes (`50%` and `85%` are accepted) and is how the numbers below were produced.
- Check each result against the last column before using it. If a probe disagrees, stop and report; do not edit a shader.

## Which route each capture uses (and why)

There are two ways to render a capture: the **4K route** (a 3840 x 2160 SubViewport over the 1280 x 720 canvas, scale 3) and the **1:1 route** (the 1280 x 720 window itself, scale 1). Some shader inputs count physical pixels (`FRAGCOORD`, `SCREEN_PIXEL_SIZE`, `LIGHT_POSITION`, `LIGHT_VERTEX`) and give different numbers on the 4K route; those must be recorded at the size they will be shown. Result for this film:

- **None of this film's shaders reads a pixel count.** `01` to `05` read only `SCREEN_UV`, a fraction of the screen (grep of `lab-shaders/` and the scene library: no `FRAGCOORD`, no `SCREEN_PIXEL_SIZE`, no light built-ins). So **C01 to C07 and C09 to C19 use the 4K route** (crisp edges at 3840 x 2160). Checked, not assumed: `run-14-route-comparison.log` compares every probe of all 19 captures between the 1:1 route (run-11) and the 4K route (run-11b): **65 probes, 65 equal within tolerance** (three-square scenes: every zone label identical; pond scenes: positions, the colours at the reflection centre and in open water within 0.015, label-map-coloured pixel counts and reflection pixel counts within a few percent).
- **One thing in the film does count pixels: the Rect-mode box of a `BackBufferCopy`.** `run-13` (both renderers, each case in its own process): on the 4K route the default box copied the top-left 101 x 101 *render* pixels, which is only 34 x 34 canvas units, whatever the node's position; a box set to (0, 0, 300, 200) copied 301 x 200 render pixels. At 1:1 (run-10) the same default box is the 100 px corner of the screen. The box is measured in render pixels, not in the node's or the canvas's units. Only **C08** uses Rect mode, so **C08 uses the 1:1 route**: `capture_scene.sh` renders it in the 1280 x 720 window itself (scale 1) and enlarges the frames 3x by whole pixels (`scale=3840:2160:flags=neighbor`: the scene is flat colour, so there is no blur). On the recorded frames the corner patch is 38 x 38 px in the window, 101 x 101 screen px, as in run-10.
- Nothing in the narration gives the size of the box (it says "a corner of the screen, wherever the node is"), so the film is true on either route; the 1:1 route makes the picture match what a viewer gets in a 1280-wide game window. The Rect box is a possible docs gap or bug (FACTCHECK 30, 71); reported to Bear, not edited anywhere shared.
