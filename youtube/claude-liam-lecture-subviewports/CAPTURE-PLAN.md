# Capture plan: SubViewports

**What this is.** Every Godot capture the build session must record for this film: 22 scene captures (C01 to C21, with C04 in two parts; C15 is a still), the editor frames, the route they are recorded on, the rules every recording follows, the result each must reproduce, and the traps already met.
**Why.** The captures are the film's evidence: the viewer watches the real engine do what the sentence says. Each one was rehearsed here, so the build session has a number to compare every recording against instead of a hope, and a clear instruction for the three things that went wrong during planning.
**Found.** All 22 captures are scenes of one library (`evidence/planning-checks/capture_scene.gd`), recorded on the SubViewport native-size route (a 3840 x 2160 SubViewport over the 1280 x 720 logical canvas), because no shader in this film reads window pixels; run-12 shows that route draws the same picture as scale 1 for all 22 scenes, in both renderers. Three things are new and the build must do them: record with the window on top (a covered Godot window is drawn on only some frames, and Movie Maker then writes repeated frames), drop or pre-roll frame 0 (it lacks the pictures in 14 scenes), and force one draw per step in any script that reads pixels. The editor frames are real and re-recordable with a driver proven here; nothing needs Bear unless that driver fails.

Paths. `R` = `csye-7270-building-virtual-environments/youtube/claude-liam-lecture-subviewports`; `S` = `csye-7270-building-virtual-environments/youtube/_godot-shaders-series`; every path below is relative to `/Users/bear/Documents/CoWork/bear-textbooks/books`.

The route was **tested, not assumed**, because this film's own pictures are SubViewports nested inside the route's SubViewport. `R/evidence/planning-checks/verify12_route_equivalence.gd` builds every scene twice in one process, once at scale 1 and once in this route, draws both in the same pass (same `TIME`), and compares the centre of every logical pixel (x, y) with 4K pixel (3x + 1, 3y + 1) at 12, 50 and 85 percent of the scene: 22 scenes, about 61 million pixels, 274 differ by more than 10 of 255 in Forward+, 269 in Compatibility and 277 under recipe B in the final run (265 to 280 in earlier runs), 262 of them stripe-edge ties in c13 decided by float rounding and the rest single pixels on moving edges, and every one has a matching pixel among the nine 4K pixels of its block (run-12, run-12b, run-12c). `verify9_nested_4k.gd` shows the nested picture appears in the same frame (no lag) and that `TIME` advances 1/30 s per rendered frame in this route.

The route in code (what `verify9` and `verify12` do):

```gdscript
var outer := SubViewport.new()
outer.size = Vector2i(3840, 2160)
outer.size_2d_override = Vector2i(1280, 720)
outer.size_2d_override_stretch = true
outer.render_target_update_mode = SubViewport.UPDATE_ALWAYS
root.add_child(outer)
var canvas := Node2D.new()
outer.add_child(canvas)
var sc := CaptureScene.new("c13")        # second argument: the folder of the shader files; the default is R/lab-shaders/
sc.build(canvas)
for f in frame_count:
    sc.update(float(f) / 30.0 * speed)   # t rises frame by frame from 0; speed is 1 unless a scene's events need re-timing (rule 6)
    await process_frame
    RenderingServer.force_draw(false)    # one real draw per step (rule 4)
    outer.get_texture().get_image().save_png(frame_path(f))
```

Numbers in this plan that count pixels or give positions on the canvas (for example the multiples of 8 in c12, or 14,187 teal pixels) are at scale 1, the 1280 x 720 canvas. In the 3x route a canvas pixel is 3 x 3 device pixels: positions are 3 times larger and counts 9 times. Nothing on screen quotes such a count; the readouts name "512 px", "128 px x4", "picture pixel" and "display pixel".

## 2. The library, the adapter and how to rehearse

## 3. Rules every capture follows

1. **Window on top.** Every Godot window the build opens for a recording or an editor frame gets `--always-on-top` (or `--position 0,0`). A window that other windows cover is drawn on only some frames (137, 136, 108 and 125 of 299 were seen, and 73 distinct frames of 400 in one Movie Maker run); Movie Maker then writes repeated frames and the clip looks frozen. With the flag, 400 of 400 frames differed, five runs (run-13c; `logs/earlier-runs/covered-window-observations.txt`). If the harness saves the SubViewport's texture itself instead of using Movie Maker, it forces one draw per step (rule 4) and the window does not matter. After every recording, count the distinct frames.
2. **30 fps, offline, fixed tick.** `--fixed-fps 30`; frame k is scene time k / 30 times `speed`. Offline capture proves nothing about real-time frame rate: say so (the video labels say "scripted" or "offline render").
3. **Frame 0 lacks the pictures** in 14 of 22 scenes (c01, c06 to c14, c16 to c19, and part of c20): a picture inside a SubViewport appears one draw after its texture is first used. Record with `skip=1` (the adapter holds frame 0 at t = 0, and the first file is dropped) or step one frame before recording (run-13b, run-13d).
4. **One real draw per step, never wait for a frame.** In any script that reads pixels: `await process_frame`, then a draw that is certain to happen, then read. Never `await RenderingServer.frame_post_draw` (it can stall for the same reason as rule 1). Update Mode Once is spent by the next **draw**, not the next frame, and a viewport only updates in a draw: c21 can come out wrong without this (run-11 O2 read 121, 176 and 305 in three runs and the right 323 in others). Two recipes are tested:
   - **Recipe A** (window on top): `RenderingServer.force_draw(false)` after each step, on top of the regular loop's own draws (run-7, run-11, run-12).
   - **Recipe B** (needs no window at all; use it in any harness that saves a SubViewport's texture itself, the 3x route included): `RenderingServer.render_loop_enabled = false` once, then per step `update(t)`, `await process_frame`, `RenderingServer.force_draw(false, 1.0 / 30.0)`, read. The regular loop never draws, so a covered window cannot matter, and the draw carries the step for shader `TIME` (below). Verified: `TIME` rises exactly 1.0 per 30 steps with 0 regular frames drawn (run-16b), c21 freezes at the same frame as under Movie Maker (run-16c), and the 3x route matches scale 1 under it (run-12c).
   Movie Maker needs the regular loop, so it takes recipe A with `--always-on-top`.
5. **Renderer and `TIME`.** Forward+ (the default) for every clip; Compatibility agrees within one level of 255 on everything measured (state the renderer on every pixel value, as the labels do). Shader `TIME` advances only in a draw, by that draw's `frame_step`: a regular loop draw passes 1/30 s under `--fixed-fps 30`, `force_draw(false)` passes 0. So with recipe A the stripes and the wobble move only on frames the regular loop really drew (a covered window freezes them, while the probes still read the `TIME` they saw), and with recipe B they move by exactly 1/30 per step. No number in the film depends on the phase (every probe reads `TIME` in the same draw), so no `--time-origin` is needed.
6. **Events and the voice.** Scene events are at fixed scene seconds chosen for 0.34 s per word and each is tied to the words in section 4. After the voice is measured, if an event lands more than 0.7 s from its words, record that scene once with `speed=` (scene seconds per clip second, for example `speed=0.93`): all of its events move together. Each clip starts at the beat's start; the tail beyond the beat is never shown.
7. **Compare every recording with the "verified result" column.** If a probe disagrees, stop and report: do not edit the shader or the scene.
8. **No input is scripted** in any capture; the only scripted things are the scene's own moves (a slide, a turn, a sweep, a switch) and they are labelled "scripted" on the video. The one beat about input (B39) is Manim.
9. **File names** are the ones the lanes use, written to `TK/runtime/remotion/public/subviewports/` (`TK` = `brutalist.art`): the column "File" below. MP4 at 30 fps for clips, PNG for the still.

## 6. Traps already met

- **The covered window** (rule 1) stalls recordings and makes waiting-only scripts read stale pictures; Once is the first casualty (run-11).
- **Frame 0** has no pictures (rule 3).
- **A premultiplied blend adds the colour of every texel**: sprites whose transparent padding still carries teal show white squares under a Premultiplied Alpha display; the scene builds those sprites with transparent black padding (`blob_image(size, false)`) and the default-blend ones with teal padding so a filtered edge never mixes in black.
- **Plain default-blend display of a transparent picture darkens soft edges** (that is B10): the pass-through comparison in c08 only reads 0.0 because the left display is a Sprite2D with Premultiplied Alpha.
- **A quarter turn hides which effect turns** (the gold moved to where the fade was strongest): c10 turns by a half turn.
- **`update(t)` must rise from 0 frame by frame**: c07, c09 and c21 fire their event once, the first time t passes it, so a jump to a late t fires it at that t (c21's Once would then freeze that moment's picture, not the 8.5 s one).
- **Reading a viewport's `get_image()` in `_ready`** or on its first frame returns an empty texture (docs: Using Viewports, Capture).
- **A 3D viewport inside the scene** (c20) needs `own_world_3d = true`, or two scenes in one process share one world.
- **zsh**: `echo ======` is a command, `set -- $var` does not split, `rm` with an unresolved glob is blocked: use explicit loops and literal paths.
- **Disk**: a 4K PNG is about 30 MB before ffmpeg; check `df -h /` first (stop under about 15 GB free).
