# Results of the planning checks: SubViewports

**What this is.** Every number the SubViewports film leans on, with the script that produced it, the log it landed in, the machine, and how to run it again. It also keeps the runs that failed, misled or proved nothing, labelled as such.
**Why.** The film's FACTCHECK.md cites these runs by name (run-1 A3, run-5 P2 and so on). If a number on screen is ever doubted, this file says where it came from and how to reproduce it.
**Found.** Everything the film claims about Godot was run, in Forward+ and, where a pixel could differ, in Compatibility, on Godot 4.7.2 (Apple M4 Pro, Metal). Three results change what the film or its build must do. A half-transparent pixel in a transparent picture is stored premultiplied, so the default blend darkens soft edges (run-5). A Quad Mesh in 2D lands the picture upside down, and a negative height fixes it, for the reason the vertex data shows (run-4). And a Godot window that other windows cover is drawn on only some frames: waiting for frames reads stale pictures and Movie Maker writes repeated frames, so every check here forces one draw per step and every recording must run with the window on top (the covered window, below).

## Machine, engine, and how to run it again

- Apple M4 Pro, macOS, Metal 4.0. Godot **4.7.2 stable (official)**. Forward+ is the default; `gl_compatibility` is run too wherever a pixel could differ. Docs read: 4.7 (docs.godotengine.org/en/stable, 2026-10-13).
- All scripts run in scratch Godot projects under `/private/tmp/claude-501/godot-shaders-subviewports/`; nothing here touches a project of Bear's or any other film.
- `./run-all-checks.sh` runs runs 1 to 12, 12c, 16 and the Shader Lab batch (about 10 minutes; `SV_SKIP_LAB=1` skips the Lab batch, which takes the Lab lock; never stop that batch with `pkill -f`, other films run scripts of the same name).
- `./run-movie-rehearsal.sh` (runs 13: the recording route, Movie Maker, about 2 minutes) and `./run-editor-labels.sh` (run 14: the real editor, about 2 minutes) are separate because they open windows for longer.
- `./run-series-driver.sh` (run 15: the film's editor frames, recorded by the series' editor driver from this film's six state scripts, about eight minutes, takes the shared Lab lock).
- `./run-cover-checks.sh` tries to cover the check window with another one on purpose. It did not reliably work (see the covered window), so it is not part of `run-all-checks.sh`.
- Every log line that carries a measurement starts with `RESULT` and is one JSON object. `logs/` holds the final logs; `logs/earlier-runs/` holds runs that misled or are kept for the record.

## Runs that failed, misled or proved nothing (kept on purpose)

1. **First versions of the fade probes (not kept as logs).** The first F3 and F4 probes sampled transparent picture pixels, where the implied alpha is 0, and read as nonsense. They were rewritten: F3 uses an opaque white fill so every pixel carries colour, F4 probes inside the blob. The rewritten checks are run-2.
2. **Camera2D check that read all zeros, then all equal (early runs of verify1).** First nothing drew the viewport (default update mode, no display), then every count was 14,187 whether or not a camera was present. The second symptom appeared only when an opaque Disabled viewport existed earlier in the script, so E5 was moved last. **Resolved on 2026-10-13:** with one forced draw per step the order no longer matters (scratch copy of verify1 with E5 first, two runs: 14,187 then 55,202 then 55,202), so the cause was almost certainly the skipped draws below, not Godot. E5 stays last as belt and braces.
3. **Pass-through comparison that failed at 0.188 (early c08).** The plain display darkened the soft edges of the moving blob while the shader display did not. That was not a bug in the scene: it is the premultiplied-alpha finding itself. The left display now uses a CanvasItemMaterial in Premultiplied Alpha mode, and run-7a c08 reads 0.0.
4. **White squares behind the blobs (early c11).** Sprite textures whose transparent padding still carried teal added colour under a premultiplied blend. The scene now builds those sprites with transparent black padding (`blob_image(size, false)`).
5. **A quarter-turn that hid which effect turns.** The gold gradient moved to where the fade was strongest, so both effects looked like they turned. The scenes turn by a half turn.
6. **Editor dock widening and a magenta mesh.** The Inspector dock did not widen when the driver asked, and a MeshInstance2D showed a magenta placeholder when the mesh scene was opened first. Neither is needed: the label text is read from the Inspector controls and the frames used are the ones taken with the main scene open.
7. **Nested-route edge metric.** An early version of the nested check compared edge pixel counts, which did not tell lag from no lag; run-9 compares the edge position against the position the scene says for that frame and for the frame before.
8. **c21 not frozen in the first full run (logs/earlier-runs/run-7c-before-forced-draws-c21-NOT-FROZEN.log).** The Once picture read 29, the live position, instead of 323. The script waited for frames instead of forcing draws; the Once was spent late (below). The same scene run alone, or with a forced draw per step, reads 323. The same first full run also read black for scene c02's picture at 8.5 s (the viewport had not been drawn yet); the forced-draw run reads the clear-coloured box with the teal blob.
9. **Update Mode Once with waiting-only frames (run-11 O2, run-11b O2, not asserted).** Read without any forced draw the right picture often shows a later moment (121, 176, 305; earlier scratch runs 31, 298, one correct 322); in the final run-11 it read the correct 323, because the window happened to be drawn on every frame. 10. **The cover window (run-10d, run-11b, run-7d).** An attempt to cover the check window on purpose. In the final scripted runs the cover did not take effect (run-10d: 300 of 300 frames drawn in every phase), so those logs prove nothing about covered windows; run-11b and run-7d still pass because they force their draws.

## The covered window (new, and the reason for `--always-on-top`)

On 2026-10-13, while chasing run-11's changing readings, I counted how many of a script's main-loop frames are really drawn. At default window placement, with other agents' Godot windows open, 299 process frames gave only 137, 136, 108 and 125 drawn frames; `--always-on-top` and `--position 0,0` gave 299 of 299 in the same minute. A recording shows the same: 400 frames of Movie Maker at default placement gave "73 frames at 30 FPS" (72 of the 400 files differ from their predecessor) and "240 frames" on other runs, with every file after the last drawn frame a repeat, while 400 of 400 differ with `--always-on-top` (five runs) and `--position 0,0` (two runs). The transcript of those runs is `logs/earlier-runs/covered-window-observations.txt`. The effect is intermittent and I could not make it appear on demand (the scripted runs in this folder mostly show every frame drawn), so the cause is **not proven**; it is consistent with a window that is behind another being treated as covered, and drawn only when it is not.

What it changes, and what is safe:
- Any script that reads pixels after waiting N frames can read a picture that was never redrawn. Every verify script here calls `RenderingServer.force_draw(false)` once per step. `await RenderingServer.frame_post_draw` can stall for the same reason.
- Update Mode Once and Update Mode When Visible are the two features where the number of draws is the point, so they are the first to go wrong: Once is spent by the next **draw**, which may be many frames after it is set (run-11).
- Shader `TIME` advances only in a draw, by that draw's frame_step: a regular loop draw passes 1/30 s under `--fixed-fps 30`, `force_draw(false)` passes 0. With waiting-only scripts or with forced draws on top of a covered window, `TIME` stands still on the frames the regular loop skipped (the c14 probe read TIME 3.3 in one run and 31.9 in another, with nothing else changed; the probes read `TIME` in the same draw, so their results stand). **Recipe B** avoids all of it for a script that saves textures itself: `RenderingServer.render_loop_enabled = false` once, then per step `await process_frame` and `RenderingServer.force_draw(false, 1.0 / 30.0)`. `TIME` then rises exactly 1.0 per 30 steps with no regular frame drawn (run-16b), Update Mode Once freezes at the right frame (run-16c, c21) and the 3x route matches scale 1 (run-12c).
- A Movie Maker recording must run with the window on top: `godot ... --always-on-top --write-movie ...`. Without it the movie can hold repeated frames and looks frozen. The same flag is used for the editor frames (`run-editor-labels.sh`).

## Not measured, on purpose

No speed, cost or frame-rate figure is quoted anywhere in the film or in these runs (the GLOSSARY forbids unmeasured speed claims). B38 says only what the docs say: Once draws one time; the default draws every frame the picture is shown. Offline capture at a fixed tick proves nothing about real-time frame rate and the captures say so.
