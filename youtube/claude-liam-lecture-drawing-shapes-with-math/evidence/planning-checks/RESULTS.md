# Planning checks: results

**What this is.** The runs behind every number and picture in `FACTCHECK.md`, in the order they matter, with the command, the result and what it means. All on Bear's Mac: Apple M4 Pro, macOS 26.5.1, Godot 4.7.2 stable (official), Forward+ (Metal) unless stated, 2026-10-13.
**Why.** So any figure on screen can be re-run, and so a reader can see how it was checked. Failed and inconclusive runs are kept and labelled.
**Found.** 72 Lab runs (17 shader files plus 11 calculators), 3 scratch scripts, one real-editor check, 4 analysis scripts and the calculator decoder. Every mask render matches an independent float64 model on every one of its 230,400 pixels. Two runs did not give an answer first time and are kept (the window that would not resize, the first typo in a scratch script); one earlier log is kept as superseded, and the first design of five pictures (replaced after a review, not because it was wrong) is kept in `superseded-first-design/`.

Re-run everything: `./run-lab-checks.sh` (about two minutes when the Lab is free, about ten when other sessions hold its lock; overwrites `png/` and `lab-results.jsonl`; then runs `run-calc.py` and the analysis scripts). Re-run a scratch script: copy it into a scratch Godot project and `godot --path <project> --script res://<file>.gd -- <absolute path of the film folder>`. The shader files' SHA-256 sums are in `shader-sha256.txt`.

## Notes on how the runs went

- The first batch of Lab runs ran at the default 640 by 360 view, not 480 by 480: my own shell script passed the options as one word (zsh does not split an unquoted variable), so the Lab ignored `--size`. It was noticed from the oval in the first picture, discarded and re-run correctly; every log above is from the corrected, consolidated script. The Lab itself is fine.
- The Lab's window cannot be shorter than 64 px: a 480 by 48 request came back 480 by 64 (the calculator's cells live in the top 48 rows; harmless).
- `hint_range(0, 1)` with integer literals, as written in the docs' own example, compiles for a float uniform.
- **Second batch (after an independent review of the layout).** The first batch of 65 runs was repeated as 66 after five pictures were redesigned: `08` and `09` (a disc with a bite and a spot instead of a cross with a gap and a dot, because the first design used `abs`, `max` and a cross before the film teaches them), and `12`, `13`, `14` (vertical arms with the same three named conditions in the same order as the crosshair, so x and y no longer swap roles silently); the crosshair's `make_arms` now computes the vertical pair first (identical pixels in all 16 crosshair renders). One calculator was added (`calc-max-equals-capped-sum`). A third batch of 72 runs followed the second review (six held pairs of the sweep videos added, and a comment-only edit to `calc/calc-values.gdshader`, whose old comments still described the first design); the shader files' SHA-256 sums were refreshed after the last edit, and no file changed after the batch started (the newest file is dated seconds before the first run). The first design's files, renders and rows are in `superseded-first-design/`.

## Side findings for the other shader films

- On Forward+ and on Compatibility, hard-edged 0/1 masks are pixel-identical; only a soft alpha blend differs, by at most 1 of 255.
- In a default project (2D HDR off), an alpha above 1 or below 0 is invisible on screen but not in arithmetic (with 2D HDR on it is visible, see `run-d`): a sum of masks can reach 2 and a subtraction can reach -1, and both survive into the next operation. This is worth one sentence in any film that adds or subtracts masks.
- `UV` and `COLOR` are not visible inside your own functions in `canvas_item` shaders; `TIME` is. The film cites exactly these three and nothing more.
